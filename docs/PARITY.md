# Паритет с оригиналом — сортировка чеклистов

Пункт плана FEAT-051. Каждая строка чеклистов паритета `docs/spec/01–04` получает здесь метку: входит ли поведение оригинала в MVP и каким пунктом `FEATURE_PLAN.md` закрывается, покрыто ли другим решением, отложено ли на этап 2 или 3, или не переносится. Правило приёмки этапа — SPEC §11.

Проверка: `node scripts/parity-check.mjs`. Скрипт сверяет пункты `- [ ]` (и отмеченные `- [x]`) в четырёх спеках со строками таблиц: число, порядок, текст, формат метки, Y/N, существование FEAT в плане и сводку. При любой непокрытой строке выход 1. С флагом `--strict` он падает ещё и пока есть строки «MVP → нет FEAT» — это ворота перед фазой C.

## Как читать

| Метка | Значение |
|---|---|
| `MVP → FEAT-NNN` | Входит в MVP, закрывается указанными пунктами плана. |
| `MVP → нет FEAT (G-N)` | Нужно в MVP, но ни один пункт плана не покрывает; см. «MVP-пункты без FEAT». |
| `Покрыто иначе → FEAT-NNN (как)` | Поведение оригинала заменено другим решением ТЗ или плана. |
| `Этап 2`, `Этап 3` | Откладывается по SPEC §9. |
| `Не переносить (причина)` | Не переносится; причина в скобках. |

- **Нужно решение пользователя = Y** — метка остаётся продуктовым решением, которое ТЗ и Clarification не закрывают. Вопросы собраны в разделе «Нужно решение пользователя».
- **ID** = `<номер спеки>-<номер пункта в чеклисте по порядку>`. Текст пункта сокращён («…»), полный — в спеке.
- **Примечание** — для исполнителя: что из пункта не попало в DoD и что из него отложено.
- Меняете чеклист в спеке — обновите таблицу и запустите скрипт.
